# План оптимизации QtCTReconstruction

Документ перечисляет конкретные точки в коде, где возможны дополнительные оптимизации, и описывает план их внедрения. Приоритеты: **P1** — высокий ожидаемый выигрыш и/или малая трудоёмкость; **P2** — средний; **P3** — рефакторинг/долгосрочное.

---

## Reference / последовательная CPU-реализация (без OpenMP)

### [P1] Чистая последовательная CPU-реализация как reference baseline
- Файлы: новые `SerialBackend.cpp` / `SerialBackend.h` (по интерфейсу `IReconstructionBackend`).
- Назначение: эталонная однопоточная реализация без `#pragma omp` и без CUDA, по возможности без SIMD-intrinsics.
- Зачем нужна:
  1. **Базис для коэффициента ускорения** в численных экспериментах (колонка «CPU (1 поток)» в таблицах статьи). Сейчас этот столбец получают ad-hoc запуском OpenMP-версии с `OMP_NUM_THREADS=1`, что не эквивалентно: `#pragma omp parallel` всё равно запускает runtime, и компилятор может сохранять часть кода под параллельными ветками.
  2. **Регрессионные тесты на корректность.** Вычислительные ошибки накопления вкладов от OpenMP/CUDA (порядок суммирования, FMA-rounding) проще отлавливать сравнением с детерминированной serial-версией.
  3. **Портативность.** Сборка на платформе без OpenMP/CUDA-toolkit (минимальная среда CI, embedded, ARM-ноутбук) для верификации алгоритма.
  4. **Учебная и документационная ценность.** Прямое отображение формул раздела 2 статьи в код, без оптимизационных слоёв.
- План реализации:
  - Файлы кода: ровно три класса — `SerialRadonForward`, `SerialFilteredBackprojection`, `SerialBackend`.
  - Никаких `#pragma omp`, `__m256`, `_mm256_*` — простые `for` циклы и `std::sin`/`std::cos`.
  - БПФ — учебный Cooley–Tukey (использовать существующий `FFT.cpp` без изменений; именно учебная природа кода тут уместна).
  - Сборку контролировать в CMake флагом `-DBUILD_SERIAL_BACKEND=ON` (по умолчанию `ON` в Debug, `OFF` в Release).
  - В `BackendFactory` добавить ветку `BackendKind::Serial`.
- Тестирование:
  - На малых объёмах ($N \le 128^3$) сравнить с OpenMP- и CUDA-версиями: разница в норме L2 не должна превышать $10^{-4}$ от ground truth для float32.
  - Время serial-реализации использовать как знаменатель в коэффициентах ускорения $A_{\text{OMP}}$, $A_{\text{GPU}}$ в Таблицах 2–4 статьи.

### [P3] Документирование serial-версии в README
- Включить раздел «Reference implementation» с пояснением, как её собрать и как соотносится с оптимизированными версиями.
- Привязать к разделу 2 статьи: каждое название функции serial-версии должно соответствовать формуле (1)–(8).

## CPU / OpenMP

### [P1] Явная векторизация горячего цикла обратной проекции
- Файл: `QtCTReconstruction/OptimizedBackprojectionCPU.cpp`, внутренний `for (x ...; x += 4)`.
- Сейчас: компилятор векторизует «как повезёт».
- План: добавить `#pragma omp simd` над хвостовым циклом по `x`; для основного — переписать на AVX2 intrinsics (`_mm256_loadu_ps`, `_mm256_fmadd_ps`, `_mm256_i32gather_ps` для `proj_row[i_k]`). Альтернатива — `std::experimental::simd`.
- Ожидание: ×1.5–2 на Skylake/Zen3.

### [P1] Параметризация размера батча углов под целевой ISA
- Файл: `QtCTReconstruction/RadonTransform.cpp`, константа `16` в `for (int b_start = 0; b_start < na; b_start += 16)`.
- Сейчас: жёстко зашитое значение 16, оптимальное только для AVX-512.
- План:
  - Ввести `constexpr int ANGLE_BATCH = ...` с выбором по макросам компилятора:
    - `__AVX512F__` → 16 (один ZMM-регистр содержит 16 float32);
    - `__AVX2__` → 8 (один YMM-регистр);
    - иначе → 4.
  - Размер батча должен совпадать с шириной SIMD-регистра, чтобы компилятор разворачивал внутренний цикл в одну SIMD-инструкцию без spill в стек.
  - Аналогичную параметризацию применить к шагу разворота по X в `OptimizedBackprojectionCPU.cpp` (сейчас 4).
- Ожидание: ×1.1–1.2 на машинах без AVX-512 (избежать spill 16-элементного батча в стек).

### [P1] Переход с собственного БПФ на FFTW3 / pocketfft / MKL
- Файл: `QtCTReconstruction/FFT.cpp`.
- Сейчас: учебный Cooley – Tukey radix-2.
- План: вынести интерфейс `FFT::forwardReal/inverseReal` за абстракцию, реализацию переключать через CMake (`-DFFT_BACKEND=FFTW`). Pinned-планы создавать один раз, повторно использовать.
- Ожидание: ×3–5 на стадии фильтрации.
- Замечание: сохранить существующий внутренний Cooley–Tukey как реализацию по умолчанию для serial-backend (см. выше) и для сборок без сторонних зависимостей.

### [P2] Кешируемые планы FFT и потоково-локальные `fftwf_plan`
- После [P1]: каждый OpenMP-поток должен иметь собственный `fftwf_plan_dft_r2c_1d` и `c2r`. План создаётся один раз в `FilteredBackprojection::reconstruct`.

### [P2] NUMA-aware `first-touch` для буферов объёма
- Файл: `OptimizedBackprojectionCPU.cpp`, аллокация `vol`.
- План: после `resize` инициализировать в `#pragma omp parallel for` нулями, чтобы страницы маппились на узлы потоков-исполнителей.

### [P3] Замена `atomicAdd` (в `RadonTransform.cpp`) на per-thread синограммы
- Сейчас: scatter в общий буфер с потенциальной ложной разделяемостью при больших `na`.
- План: каждый поток пишет в собственную `Buffer2D`, в конце `#pragma omp parallel for collapse(2)` агрегирует. Полезно при `nz < num_threads`.

## GPU / CUDA

### [P1] Texture memory для backprojection
- Файл: `QtCTReconstruction/CUDAPureBackend.cu`, `gpVolumeBackprojectionKernel`.
- План: создать `cudaTextureObject_t` поверх `filt_projs` с `cudaFilterModeLinear` — встроенная аппаратная билинейная интерполяция убирает ручные `row[u0] + fu*(row[u0+1]-row[u0])` и даёт более широкий 2D-кеш.
- Ожидание: ×1.3–1.8.

### [P1] Pinned host memory + `cudaMemcpyAsync` в `CUDABackend`
- Файл: `CUDABackend.cu`, инициализация `m_h_*` буферов.
- Сейчас: обычный pageable host. План: `cudaHostAlloc(..., cudaHostAllocPortable | cudaHostAllocWriteCombined)` — пропускная способность H→D вырастает с 6 до 12 ГБ/с на PCIe 3.0 x16.

### [P1] Двойная буферизация с двумя CUDA-stream
- Файл: `CUDABackend.cu::reconstructVolume`.
- План: переписать цикл в pipeline: stream A копирует слой $z+1$ пока stream B вычисляет слой $z$, синхронизация только по событиям.
- Ожидание: ×1.4 на гибриде (скрытие PCIe).

### [P2] Слияние ядер `normalize` + `radonForwardScatter`
- Файлы: `CUDABackend.cu`, `CUDAPureBackend.cu`.
- План: одно ядро читает воксел, нормализует, вычисляет вклады во все углы. Экономит один полный проход по `m_d_vol_in` (сейчас ~16 ГБ для $1024^3$).

### [P2] Слияние filter-multiply + back-projection scaling в одно ядро
- Файл: `CUDAPureBackend.cu`.
- Сейчас: отдельное ядро поточечного умножения спектра на $H_k$, затем отдельное обратное БПФ, затем backprojection с делением на $\pi/N_\theta$.
- План: финальный множитель $\pi/N_\theta$ внести в фильтр $H_k$ при предвычислении (на CPU). Экономит одно ядро и один проход по `vol_out`.

### [P2] Shared memory для фильтра
- Файл: `CUDAPureBackend.cu`, kernel умножения спектра.
- План: загружать `filter[k]` для блока в `__shared__ float s_filter[BLOCK]` один раз — все нити блока, обрабатывающие один и тот же $k$ для разных проекций, читают из shared.

### [P2] Auto-tuning размера блока через `cudaOccupancyMaxPotentialBlockSize`
- При сборке под Ampere/Ada оптимум блока для backprojection — 8×8×8 (512 нитей). Замерить и зафиксировать.

### [P3] Warp-level reduction для min/max в нормализации
- Файл: `CUDABackend.cu` использует `thrust::min_element`/`max_element` (две полные scan'а по объёму).
- План: ядро на `__shfl_xor_sync` + `atomicMin/Max` в shared — одно прохождение, без зависимости от Thrust.

### [P3] Multi-GPU через `omp_set_num_threads(num_gpus)` + `cudaSetDevice`
- На уровне `BackendFactory` добавить выбор числа GPU; в `CUDAPureBackend` — разбиение по диапазонам $z$.

## Гибридная схема CPU+GPU

### [P2] Полезная работа CPU параллельно с GPU
- Файл: `CUDABackend.cu::reconstructVolume`.
- Сейчас: CPU простаивает в `cudaDeviceSynchronize` между ядрами и копированиями.
- План: вынести на CPU-thread (через `std::async` или OpenMP-task) задачи, которые выполняются для следующих/предыдущих срезов:
  - Чтение/декомпрессия проекций следующего слоя с диска.
  - Сборка финального тома в host-памяти из готовых срезов.
  - Постобработка (фильтрация шума, экспорт).
  - Подготовка тригонометрии и фильтра для следующего батча углов в pinned-буфере.
- Ожидание: 5–15 % на больших объёмах за счёт скрытия I/O.

### [P3] Streaming / online-режим
- Файл: новая обвязка `StreamingController.cpp`.
- Сейчас: реконструкция начинается после загрузки всех проекций.
- План: обработка проекций по мере их поступления (с детектора, с диска). Архитектурно — producer/consumer-очередь между потоком чтения и обрабатывающими CUDA-stream'ами; ограничение — нужно $\ge \pi$ радиан углов для начала обратной проекции среза.
- Применимо для синхротронных и индустриальных установок с непрерывным сбором.

## Архитектура / прочее

### [P2] Удаление мьютексов и общего состояния в `CtReconstructionController`
- Проверить, нет ли блокировок UI-thread'ом во время `reconstruct()`.

### [P2] Замер и логирование времени по стадиям через `nvtxRangePush/Pop`
- Включает профилирование в Nsight Systems без перекомпиляции.
- Дополнительно: добавить лёгкую обвязку `Timer` на CPU-стороне (`std::chrono::high_resolution_clock`) с записью в CSV для регрессионного отслеживания производительности между коммитами.

### [P2] Покрытие unit-тестами на ground-truth фантоме Шеппа – Логана с метриками
- В каждом backend'е (Serial, OpenMP, CUDA, Hybrid) сравнивать реконструкцию с аналитическим решением.
- Метрики:
  - **L2-норма ошибки** относительно ground truth (для float32 ожидать $\le 10^{-3}$ при $N_\theta \ge 360$);
  - **PSNR** ≥ 35 dB при $N = 256^3$, $N_\theta = 720$;
  - **SSIM** ≥ 0.95 в центральном срезе фантома.
- Параметры эллипсоидов: см. таблицу 3.1 в Kak/Slaney 1988.
- Запуск в CI: на каждый PR автоматически прогон Serial-backend'а и сравнение с эталоном; на релизы — полный набор по всем backend'ам.

### [P3] Регрессионное профилирование производительности
- В CI на nightly-сборках: запускать набор бенчмарков ($N \in \{128, 256, 512\}^3$, $N_\theta \in \{180, 360, 720\}$), сохранять время выполнения в CSV, отслеживать тренды.
- Цель: ловить performance-регрессии раньше, чем при ручном замере перед релизом.

## Порядок внедрения

1. **Спринт 0 (baseline):** [P1] Serial-реализация + unit-тесты на Шеппа–Логана с PSNR/SSIM.
2. **Спринт 1 (CPU):** [P1] FFTW + потоково-локальные планы + SIMD-intrinsics на BP + параметризация размера батча.
3. **Спринт 2 (GPU):** [P1] texture memory + pinned + двойная буферизация.
4. **Спринт 3 (гибрид):** [P2] полезная работа CPU параллельно с GPU + слияние ядер + shared memory для фильтра + auto-tuning.
5. **Спринт 4 (масштаб):** [P3] multi-GPU, NUMA-aware размещение, streaming-режим, регрессионное профилирование в CI.
